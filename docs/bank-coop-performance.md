# 多人银行室内战斗性能测试 · 2026-10-18

本轮测试对象为当前银行联机协议 2 / bank-combat-v4。新增多人性能驱动、可重复案例和联机 CPU 分段采样，目标是区分客户端渲染、感染者呈现、服务端模拟及网络复制的成本。没有改变正式游戏画质、感染者数量、伤害或网络频率。

[完整表格与场景实拍](../project/evidence/bank-coop-performance-20261018/gallery.html) · [逐轮 CSV](../project/evidence/bank-coop-performance-20261018/metrics.csv) · [原始数据及源码快照](../project/evidence/bank-coop-performance-20261018/raw-evidence.zip)。最终采样：`logs/performance/bank-coop-20261018-054954`。22 次正式采样均满足有效战斗、实际装填、连接/数量不变与采样完整性检查；另有 15 项联机玩法回归和 4 项统计口径检查通过。**这不表示每个压力档达到了 60 FPS / 60 Hz。**

## 实测结果

机器为 i9-13900HX / RTX 5070 Ti Laptop，Windows，Godot 4.7.2 调试构建；下面是默认 1920×1080、原画质的两轮范围。每例初始参与数量固定，活体会自然变为尸体；完整结果保留每秒的活体、尸体、击杀和弹药变化。

| --- | ---: | ---: | ---: | ---: |
| 大厅，2 人 / 32 敌 | 93.8–116.7 | 12.46–14.55 | 7.70–8.32 | 约 60 |
| 大厅，4 人 / 32 敌 | 74.4–91.5 | 15.15–17.96 | 9.86–12.10 | 约 60 |
| 大厅，4 人 / 64 敌 | 60.0–74.1 | 19.00–24.42 | 18.60–20.69 | 58.2–60.0 |
| 大厅，4 人 / 84 敌 | 53.8–65.7 | 23.99–27.82 | 22.57–23.58 | 48.8–55.1 |
| 现金办公区，4 人 / 32 敌 | 85.3–86.8 | 14.99–15.07 | 11.88–12.81 | 约 60 |
| 三楼活动区，4 人 / 32 敌 | 94.8–100.3 | 13.85–14.65 | 9.15–11.05 | 约 60 |

84 敌大厅的 1% Low 只有 **32.8–34.9 FPS**，服务器快照实际到达约 **8.2–9.2 Hz**。本轮没有注入延迟或丢包；服务端 CPU 超预算已经会降低世界更新频率。四人 32 敌大厅也有一轮帧 P95 超过 16.67 ms，不能只凭平均 FPS 高于 60 就称稳定锁帧。

## 瓶颈判断

**服务端首先受感染者模拟限制。** 84 敌大厅的感染者区段约占整体脚本耗时 94%。以下为两轮的平均区段耗时范围，单位 ms/物理步，子区段不能重复相加：

| 区段 | 平均耗时范围 | 含义 |
| --- | ---: | --- |
| 感染者总更新 | 15.43–17.60 | 服务端主要成本 |
| 姿态采样 | 4.62–5.63 | 已包含命中体更新 |
| 碰撞移动 | 4.57–5.54 | 密集接触和扫掠 |
| 布娃娃 | 0.76–1.43 | 受死亡/补射轨迹影响，部分尾部更高 |
| 群体避让 | 0.99–1.19 | 近邻查询及分离计算 |
| 寻路 | 0.046–0.056 | 不是本轮主瓶颈 |
| 快照构建/发送 | 0.396–0.411 | 按每物理步平均，实际世界包每六步发送一次 |

该档服务端进程 CPU 约为一个逻辑核心的 107%–109%（包括工作线程），与脚本超预算相吻合。直接提高 tick 会增加已有的每秒计算量；应先压低单步成本。

**客户端动态阴影的提交和渲染成本明显。** 同大厅 84 敌的诊断结果如下，均仍在真实战斗中，未替换正式设置：

| 设置 | 平均 FPS，两轮范围 | 世界 GPU 平均 ms | 世界渲染 CPU 平均 ms | 平均绘制次数 |
| --- | ---: | ---: | ---: | ---: |
| 默认 1080p | 53.8–65.7 | 4.70–4.90 | 3.55–4.37 | 2432–3263 |
| 1080p，渲染比例 0.5 | 48.9–54.6 | 2.53–2.71 | 4.21–5.17 | 3129–3944 |
| 1080p，关闭阴影 | 109.2–111.0 | 2.12–2.21 | 1.58–1.72 | 238–289 |

降低分辨率确实减少了 GPU 时间，却未改善整体帧时间；关闭阴影同时显著减少绘制和渲染 CPU 成本。这支持优先优化动态阴影的投影者/提交数量，而不是先整体降低纹理或分辨率。不能把关闭阴影的 FPS 当作保留当前画质后必然获得的收益；各轮接触轨迹、尸体和镜头可见物不同，服务器也有掉 tick，结果只是成本隔离证据。

原生 1440p 的大厅 84 敌为 50.8–52.7 FPS、帧 P95 27.10–27.61 ms。客户端自身每个物理步的世界呈现约 5.06–5.18 ms，其中姿态约 3.44–3.62 ms；即使远端模拟优化完成，客户端呈现也仍需要独立处理。

**带宽与内存需要分别看。** 四人原画质案例服务端发送约 **334–564 KiB/s（约 2.74–4.62 Mbit/s）**，接收约 140 多 KiB/s，尚未模拟弱网重传。84 敌档发送量有时更低，是发送频率随服务器 tick 下降及战斗状态不同，不能解释为更省资源。服务端短时 RSS 峰值约 **632 MiB**，渲染客户端约 2.2 GiB；对你的 4GB/2核 VPS，当前证据更提示优先核实单核计算能力和可用上行带宽，不能据本机内存数值宣称 VPS 已能稳定运行 84 同屏战斗。

```powershell
# 另加同大厅的 1440p、半渲染比例、关闭阴影诊断

.venv/Scripts/python.exe -m game.tests.benchmark_coop_combat --project bank --cases hall_4p_84 cash_4p_32 --repeat 2
```

案例在 `game/tests/coop_combat_performance_suite.json`，正常输入驱动在 `game/tests/coop_combat_performance.gd`，调度/汇总在 `game/tests/benchmark_coop_combat.py`。采样结果写入独立 `logs/performance/bank-coop-<时间>/`，包括每进程原始帧/物理步、源码哈希、输入请求、初始布点、操作系统 CPU/内存样本、引擎日志和实际画面。原始失败不覆盖。

## 方法与验收

- 一个独立无渲染服务端，一个真实渲染客户端，其余 1 或 3 个无渲染客户端。全部运行当前银行代码和真实 ENet 连接。不会把无渲染进程的循环频率当成游戏 FPS，也不会把同一显卡渲染四个窗口的结果当成单个玩家体验。
- 默认 1920×1080、原生 1.0 渲染比例、Forward+、原有 MSAA/吊灯/烘焙；关闭垂直同步与客户端 FPS 上限，物理目标 60 Hz。独立进程仍共用本机 CPU、内存和散热，不能等同于远端服务器加独立玩家电脑。
- 每个案例从导航点选择可站位置，检查完整胶囊与静态世界碰撞，并保留角色间距。全部预检后才开始正式统计。当前资源总是加载 84 个感染者对象；数量档指其中参与战斗的数量，并不减少预加载资源。
- 布点后只通过正常键鼠事件瞄准、开火、装填、推开、侧移和挣脱。不会调用伤害/击杀回调。高血量 10000 仅在初始夹具设置一次，用于维持负载；敌人伤害和抓取照常执行，不是正常血量生存性验证。武器仍使用正常弹匣容量和装填。
- 检查玩家实际开火、共同击杀、受到敌人伤害、连接和总参与数量保持、无人进入死亡菜单、采样未截断。活体会变成尸体，逐秒记录活体/尸体和击杀；不是每帧保持相同活体数量的人工恒定负载。
- 各进程按共同墙钟开始预热/采样。测量窗口中不查询控制文件、不截图、不写盘。结束后才保存数据和截图；不是固定步进桥中的“FPS”。
- 截图上的 HUD FPS 是采样结束后静止画面的即时值，不能拿来替代报告中的实时窗口统计。
- 报告包括平均 FPS、最慢 1% 帧平均耗时的倒数、帧耗时 P95/P99、超 50 ms 帧数、服务器实际 tick Hz、脚本分段、视口 GPU 时间、绘制次数、ENet 吞吐、快照间隔、进程 CPU 与内存。

CPU 区段有包含关系：`server_infected` 包含姿态、移动、寻路、群体避让和布娃娃，`pose` 又包含命中体更新；不能把所有区段相加。CPU 与 GPU 的流水线时间也不能直接相加。RPC 接收和部分渲染提交不在 `advance` 的脚本区段内，但仍体现在进程/帧间隔中。GPU 的零值记录为不可用。

操作系统 CPU 100% 表示占满一个逻辑核心；RSS 为驻留内存，private 为私有提交量，两者不能相加。ENet 字节数是传输库统计，不是运营商链路计费值。诊断关闭阴影或降低比例只用于归因，不是已经交付的优化。

## 已知测量边界

这是本机调试构建的短时性能诊断，不是 Ubuntu VPS 压测，也不是几小时的内存/热稳定性验证。笔记本功耗、温度与后台争用会影响数值；即使同一输入策略、相同随机种子，也不保证并行网络和物理接触轨迹逐帧一致。比较时同时看两轮范围、战斗结果和负载变化，不能只选最快的一轮。

当前调度器使用 Windows 进程 API 采样 CPU/内存，不能直接当作 Ubuntu 采集脚本。Godot 路线可以复用，后续远端测试需补 Linux 进程采样，并测试四人分散在不同楼层作战；这轮五种室内区域分别测试，队伍在每例中集中在同一区域。

自动瞄准路线会进入近身拥挤状态；实拍中可见队友贴脸遮挡和模型相交。保留这些真实画面，不以它们推断最终美术合格；这些视角也不等同于无遮挡的室内全景，不能将本表扩展成所有镜头的性能保证。

首轮输入校验发现射击与推开锁定时间重叠，导致手枪几乎未开火；该样本判为失败并保留。正式路线将开火安排在动作锁定结束后，并通过输入处理器补充正常挣脱，保留足够开火/击杀断言。已有渲染进程退出 Texture RID 警告单独保留，不据此宣称长期资源无泄漏。

第一版完整矩阵的截图复核还发现，周期性推开会打断装填。最终路线在弹药不足或装填期间抑制推开，以正常按 R 提前装填，并记录服务端弹匣实际增加的弹数。16 秒及以上案例必须至少发生一次真实装填完成；第一版矩阵归入过程证据，不混入最终基线。

## 优化实施顺序

1. **先降低密集战斗的服务端单步成本，保持 60 Hz 目标。** 拆分角色姿态与命中体更新，检查共享姿态采样、重复骨骼查询和不活跃角色的无效工作；对远离所有玩家的非战斗角色做有上限的更新调度。近身攻击、抓取、被击中角色仍优先更新，不能简单关掉服务端骨骼而破坏头部/肢体命中。密集移动要继续检查接触解算和休眠条件；布娃娃已经有休眠，重点在仍清醒的尸体与补射唤醒。验收目标先设为压力档服务端 P95 ≤ 14 ms、实际 60 Hz，给复制和调度留余量；这只是目标，尚未完成优化。
2. **减少客户端动态阴影提交。** 现有楼层灯光裁剪已启用，下一步针对房间边界、实际光照范围和投影者数量进一步限制；近处人、门和关键灯保留完整投影，远处尝试简化阴影网格或分级更新。结合绘制次数和渲染提交耗时确认收益，再检查大厅、楼梯、门边和手电下的阴影跳变、漏光及脚部接触。整场关闭阴影只用于诊断，不作为推荐画质配置。
3. **跳过客户端不需要更新的角色呈现。** 当前 `world_presentation.gd` 的遍历没有先排除 `active=false` 的角色，隐藏角色也可能进入姿态路径；稳定不动的尸体仍反复应用关节姿态。优先增加明确的活动/脏状态判断，再做距离、可见性分级。复现时需检查重新出现、死亡、爆头、迟加入和重连，防止骨骼或姿态停在旧状态。骨骼采样、命中体和尸体变换有包含关系，不能把各计时直接相加估算收益。
4. **压缩复制量并保持现有弱网保护。** 当前所有角色、门和队伍仍发送完整快照；静置尸体和不活跃对象适合改成变化驱动，远处对象可降低复制频率，保留可靠初始化/关键帧和恢复路径。客户端近期输入也可以做紧凑编码，保留冗余、序号和校验，不能仅删掉重传兜底。涉及协议变化必须成对更新并重跑丢包、乱序、加入/重开竞态与自动重连用例。
5. **最后评估服务端资源裁剪和更大规模扩展。** 当前测试最多 84 个感染者，不是上千实体测试。若上述优化后仍不够，再考虑服务端专用碰撞/动画资源、重计算迁移到原生模块、按房间控制同时接战规模；都需要新的行为和画面回归。不要在缺少实测时把升级 VPS 或增加服务器 tick 当成已经解决问题。

每次只改一类成本，使用同一套案例重复测量，同时对照击杀、实际装填、活体/尸体数量、CPU/GPU 区段和网络频率。单纯平均 FPS 上升，而服务器掉 tick、射击停止或敌人数量减少，不能判作有效优化。正式画质及玩法修改应另行实施，本轮仅交付测量和方案。
