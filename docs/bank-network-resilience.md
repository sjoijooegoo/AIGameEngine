# 银行联机弱网实测与加固计划

后续：2026-10-18 已交付[弱网加固与新版本说明](bank-network-hardening.md)。本文保留 2026-10-17 旧试玩包的审计结果，不代表新版的实测结论。

2026-10-17：以前的检查覆盖本机真实 UDP 连接、容量、退出重连、断线清理和两人战斗，**没有覆盖延迟、抖动和高丢包矩阵**。本轮补了实际网络注入测试。结论是基础功能可以联机，但当前版本不能称为已经通过弱网稳定性验收。

本轮只增加测试与报告，未修改正式联机实现。受测运行时与最近交付的 `build/bank/combat-coop/20261017-193936/windows/package/BankCoop.exe` 对应源码核对，详见证据中的 `source_comparison`。WSL 常驻服务和试玩 EXE 没有在本轮更新。

## 测试条件

- 当前 `game/runtime/` 银行场景，Godot 4.7.2，真实专用服务端进程和两个真实客户端进程，全程 headless；保留 84 个感染者的世界同步数据。
- 每名客户端经过独立的 loopback UDP 代理；不改协议负载，不修改操作系统网络配置。客户端与服务器之间的握手、确认、重传都经过代理。
- 表中延迟为**注入的额外往返延迟 RTT**，两个方向各一半。实际 ENet RTT 还包括本机调度；丢包比例为**每方向 UDP 数据报独立随机丢包**。抖动为每方向独立均匀分布的正负偏移，最低为零延迟；重复包单独注入。
- 先通过正常 UI 加入，再用正常键鼠输入移动、停止、单发射击和开门。fixture 只设置测试起点。每个完成用例额外采样约 10 秒稳态，不等于整场合作通关或长时压力测试。
- 移动响应从客户端输入处理时刻量到角色位移超过 0.08 米；开火响应看服务端与两名客户端弹药/射击状态收敛。逐帧采样在各 Godot 进程内部，避免将 Python 轮询等待误计为网络延迟。加入、开门完成和断网停走时间仍是控制器观测上界。
- 网络重传必须使用真实时间与正常 60 Hz 调度，不能用固定步进或加速模拟代替。本驱动没有修改正式玩法参数，也不会导出到发行包。

## 实测结果

下面的 Hz 是客户端接收**完整世界快照**的频率，不是渲染帧率。快照正常目标为 10 Hz；玩家移动另走 20 Hz 快照。服务器模拟在完成的用例中维持约 60 Hz。

| 注入条件 | 按键到角色明显移动 | 完整世界快照到达 | 观察与判断 |
| --- | ---: | ---: | --- |
| 本机无注入 | 103–116 ms | 约 10 Hz | 流程完成，已有插值等待 |
| 100 ms RTT，±10 ms 抖动 | 236–241 ms | 约 10 Hz | 移动、开火、开门完成；操作开始有可见延迟 |
| 200 ms RTT，±25 ms 抖动 | 319–323 ms | 约 10 Hz | 流程完成；没有本地移动预测，延迟直接影响手感 |
| 300 ms RTT，无抖动/丢包 | 430 ms | 约 10 Hz | 流程完成；快照正常仍不代表响应及时 |
| 300 ms RTT，±40 ms，5% 丢包 | 404–417 ms | 8.2–9.0 Hz | 最长更新间隔约 333 ms |
| 500 ms RTT，无抖动/丢包 | 606 ms | 约 10 Hz | 流程完成，但明显迟钝 |
| 500 ms RTT，±75 ms，5% 丢包 | 683–718 ms | 4.7–5.5 Hz | 最长更新间隔约 845 ms，现有 100 ms 插值缓冲无法填补 |
| 800 ms RTT，无抖动/丢包 | 934 ms | 两人分别约 10.2 / 5.2 Hz | 流程完成，一名客户端最长约 996 ms 没有新完整快照；还需排查收包及 ENet 自适应行为 |
| 800 ms RTT，±100 ms，10% 丢包，两轮重测 | 912–1048 ms | 2.6–2.9 Hz | 可以完成操作，更新间隔 P95 为 683–734 ms，最长约 1 秒；不能视为可流畅合作 |
| 200 ms RTT，±40 ms，20% 丢包，重测 | 369 ms | 2.8–4.9 Hz | 操作完成，但最长更新空档达到 1433 ms |
| 300 ms RTT，±80 ms，30% 丢包 | 不给出有效响应结论 | 未完成 | 首轮出现加入失败/中途断线；有序重测加入约 10.2 秒后断开；最终代理修正后仍有握手失败，无法完成双人加入 |
| 200 ms RTT，±140 ms，2% 丢包、3% 重复包 | 234–305 ms | 2.2–2.7 Hz | 流程完成，但世界更新空档约 0.7–1.1 秒；移动通道较快不能掩盖敌人/门状态落后 |

各行来源和重复次数见 CSV，不把不同条件合并成成功率。第一轮为 9 条件 × 2 次；修正测试等待后重测 5 个条件各 1 次；另加 3 个纯延迟条件各 1 次；修正代理退出事件处理后再跑本机、800 ms+10%、300 ms+30% 各 1 次，共 29 例。重复次数不足以推断稳定可用率。

短暂断网另有两例：一名玩家断网 3 秒后原会话恢复；断网 12 秒时客户端约 8.19 秒退出，恢复后手动重进约 656 ms，另一名玩家仍留在会话。断网后服务端停止原移动的控制器观测上界约 0.47–0.52 秒；代码的输入陈旧阈值为 18 tick（约 300 ms），两者不能当作同一种测量。

## 失败记录与测试修正

第一轮 18 个用例有 13 个完成、5 个失败，且 Bravo 日志有 68 条认证状态收包错误，整轮非零退出。原始 JSON、日志和输入追踪完整保留在 `initial-matrix-raw.zip`。

发现第一版测试只等客户端看到相同的回合编号；世界快照使用不可靠通道，而重置 RPC 使用可靠通道。前者先到不能证明后者到达，迟到的重置可能清除测试正在按下的输入。因此不能把首轮高丢包下的所有移动、射击、门超时直接判成正式玩法缺陷。

第二版仅在 debug 驱动增加与重置同一可靠通道的有序标记，等两名客户端收到后才开始输入。正常输入仍走原处理器；未直接调用玩法回调来制造成功。重测 800 ms+10% 和 200 ms+20% 能完成操作，30% 丢包仍在准备阶段断线。修正测试没有改善正式协议，严重快照空档依然存在。

最后校验还发现旧代理在 Windows 上收到 UDP 端口关闭通知（WinError 10054）会停止转发；旧报告在退出清理后才采集代理状态，没有通知时间。因此这些报告中的代理错误不能隐去，旧失败的因果判断必须保留限制。完成用例在采样结束仍收到世界快照，但不能据此断言所有代理错误都发生在清理之后。

第三版代理对已关闭端点的通知记录时间并继续处理其他端点；添加退出后仍能转发的契约检查，同时在清理前、清理后分别保存代理状态。最后 3 例中代理没有致命异常；800 ms+10% 采样期间没有端口关闭通知，仍出现约 1 秒更新间隔；30% 丢包仍无法完成两人加入，一名客户端报握手失败。这样确认严重弱网结论没有依赖旧代理退出问题。该轮的原始证据为 `proxy-lifecycle-retest-raw.zip`。

首轮认证错误对应 Godot 在认证未完成时收到其他类型包的检查。复测未重现；包时序/握手边界是排查方向，尚未证实唯一根因，不能以过滤日志或增加等待秒数宣称解决。参考 [Godot SceneMultiplayer 实现](https://github.com/godotengine/godot/blob/4.7-stable/modules/multiplayer/scene_multiplayer.cpp)。失败用例的部分耗时只有控制器观测上界，不能与完成用例的逐帧耗时合并统计。

`completed` 只表示该次有界操作收敛。弱网质量仍不合格，报告中保留此结论；退出码非零时应检查具体失败阶段和日志。

## 已有的稳定性措施

| 机制 | 当前实现及边界 |
| --- | --- |
| 服务端权威 | 移动碰撞、伤害、弹药、门和敌人都在服务端模拟；客户端显示收到的状态 |
| 消息分类 | 移动输入持续更新，状态快照用不可靠通道；操作请求和定期关键帧使用可靠通道 |
| 去重与校验 | 输入/动作序号单调检查，有限数值和动作白名单，动作队列及速率上限 |
| 输入失联保护 | 18 tick 没有新输入后停止移动并清理开火输入，避免一直走或一直射击 |
| 状态恢复 | 世界快照约 10 Hz、每秒可靠全量关键帧；客户端超时退出；支持手动重新加入 |
| 数据上限 | 压缩分片、有限解压长度，不允许对象反序列化 |
| 视觉平滑 | 队友位置插值；最近试玩版门与感染者采用固定约 100 ms 缓冲并连续播放动作 |

ENet 可靠消息包含重传，且会根据 RTT 波动调整不可靠消息发送比例；这不能替代游戏层的预测、状态去旧和重连策略。参考 [Godot ENetPacketPeer 文档](https://docs.godotengine.org/en/stable/classes/class_enetpacketpeer.html)。本测试未修改引擎限速或超时参数。

## 建议加固顺序（尚未实现）

1. **先处理快照与会话时序。** 当前分片接收只缓存一个 tick，新 tick 第一片到来就丢弃上一份未完成快照，乱序/抖动会进一步放大丢包。改成有数量、字节和 TTL 上限的多快照组装窗口，完成后按单调 tick 接受；增加丢片、快照年龄和到达间隔计数。回合重置、迟加入与首帧需要明确的版本/确认屏障，旧回合事件不得覆盖新状态。复现认证收包错误后再修复其发送边界。
2. **让本地操作及时响应。** 本地移动采用输入预测，服务端确认序号后校正并重放未确认输入；服务器继续决定合法位置。枪口、后坐力和声音可先本地表现，再按权威弹药与命中结果校正。命中判定如加入回溯，需要限制历史长度并结合客户端时间校验，不能让客户端直接报伤害。
3. **适应抖动并控制过时数据。** 根据快照到达间隔调整插值缓冲，短时间缺包允许有限外推，超限停止而非无限推算。连续输入保留最新状态和少量冗余，可靠操作与高频确认避免互相长期阻塞；动作应有会话/回合标识与有限有效期。重连或长停顿后不能补执行数秒前的开火。
4. **加入明确恢复流程。** 显示 RTT、世界快照年龄和网络不稳定状态；区分连接中、同步中、已连接、暂时失联和已退出。指数退避重连，使用有时限的会话恢复凭证保留角色状态，先收完整快照再恢复输入，正确释放/保留四人名额。当前手动重进会创建新玩家状态，不能当作无损恢复。
5. **建立上线门槛。** 在上述改造后重跑同条件矩阵，再补突发丢包、限带宽、上下行不对称、连续快速重连、服务器重启、四人 30–60 分钟合作战斗，以及实际 2 核 Ubuntu VPS。分别检查正确性、输入延迟、快照空档、内存/队列是否增长和用户实际观感。

单纯把 60 Hz 提到更高无法消除 RTT，也不能让缺失分片自动完整；它还会增加小型 VPS 的负担。本轮没有真实 VPS、渲染帧率、NAT 切换、带宽上限、突发丢包或长时容量证据。单人和局域网通过不能替代这些检查。

## 重跑

```powershell
# 独立代理契约检查，不启动旧试验场
.venv/Scripts/python.exe -m unittest game.tests.test_network_fault_proxy -v

# 全矩阵，两个不同种子；包含 3 秒和 12 秒断网
.venv/Scripts/python.exe -m game.tests.verify_network_resilience --project bank --repeat 2 --sample-seconds 10

# 只测纯延迟
.venv/Scripts/python.exe -m game.tests.verify_network_resilience --project bank --repeat 1 --profiles rtt300 rtt500 rtt800 --sample-seconds 10 --skip-outages

# 定向复测严重丢包和乱序
.venv/Scripts/python.exe -m game.tests.verify_network_resilience --project bank --repeat 1 --profiles rtt800_loss10 rtt200_loss20 rtt300_loss30 reorder_duplicate --sample-seconds 10 --skip-outages
```

每次创建独立 `logs/sessions/bank-network-*`，保存三进程启动命令、engine.log、trace.jsonl、逐帧遥测、每方向实际注入计数和报告。随机种子保存在报告中；操作系统调度会影响报文顺序，不声称相同种子能逐包完全复现。代理有队列容量上限，检查 `overflow_dropped`、`error` 和端口通知时间，不能将代理自身过载算成正式网络问题。本轮所有代理均无队列溢出；旧版本的 10054 中止问题和第三版复核单独列于上文。

稳定证据归档在 `project/evidence/bank-network-resilience-20261017/`，含原始 ZIP 和 SHA-256 清单。首轮轮询采样试跑 `bank-network-20261017-201355` 只用于检查工具连通性，未被用作本文延迟/快照频率结论。
